## v4 — 2026-08-19 (ERD adoption for master data)

- **Source**: `docs/MMS_Weighbridge_ERD_Operational_MVP_v3.1.mermaid` — discovered mid-checkpoint for screen-029, never previously consulted by Phase 3 (tech-1-core) when entity-catalog v1-v3 were written. User confirmed via 2 explicit AskUserQuestion rounds: (1) full ERD adoption, rework screen-027/028 — CONFIRMED; (2) keep `id` as uuid PK for corporate/company/business-unit (NOT the ERD's literal `corporate_code`/`company_code`/`business_unit_code` as primary key) to avoid cascading FK-type changes into already-shipped `Station.business_unit_id`/`User.business_unit_id` (uuid) across screens 001-004/006-018 — CONFIRMED "tetap uuid PK, kode jadi field terpisah".
- **corporate_code/company_code added as separate unique business-identifier fields** (not PK) ← direct consequence of the PK-strategy confirmation above.
- **business-unit's existing `code` field kept as-is** (not renamed to `business_unit_code`) — it already existed pre-ERD and nothing forced a rename; only corporate/company got the new `*_code` naming since they had no code field at all before. Flagged as a minor naming inconsistency (corporate_code/company_code vs plain code) — deliberate, to minimize churn.
- **company.name kept its existing "unique per corporate" rule AND company_code is globally unique** — these two rules coexist rather than replacing one another; ERD's code-as-PK semantics imply company_code should be globally unique (PKs are inherently globally unique), while the pre-existing per-corporate name-uniqueness rule (screen-028's whole design point) is preserved since the ERD doesn't contradict it.
- **station.type enum KEPT despite not existing in the ERD literal** — this field is load-bearing for already-implemented mobile screens (006 Station List, 007-009 Monitor) that filter/route by station type. Removing it to match the ERD literally would break shipped, tested functionality. Explicitly flagged as an intentional divergence from the ERD, not an oversight.
- **station.no_of_machinery_group and machinery-group.no_of_equipment treated as COMPUTED (COUNT), not stored/manually-entered columns** — even though the ERD lists them as plain columns, this app's established pattern throughout (company_count, business_unit_count, station_count) computes such counts via `withCount()` rather than storing a denormalized number an Admin could get out of sync. Kept consistent with that pattern rather than introducing a new stored-and-drifting count field.
- **machinery.description/picture_url used instead of the old entity-catalog's notes/picture field names** — safe rename since screen-031 (Kelola Machinery) was never implemented; adopted the ERD's exact naming with zero migration cost.
- **New entities machinery-group, machinery-insurance, machinery-tax-purchase added** ← per user's explicit "full scope" choice (groups as own entity/screen, insurance+tax as child-grids within Kelola Machinery). This also required adding a brand-new screen-033--kelola-machinery-group (not previously in the 32-screen scope) since machinery_group has its own meaningful standalone fields (workshop_factor, cost_per_equipment) an Admin manages directly, consistent with how Station already gets its own screen despite being "under" Business Unit hierarchically.
- **ERD's `synced_at` fields on machinery/machinery_groups/insurances/tax_purchases intentionally OMITTED** — PRD's confirmed assumption states master data is Admin-only via web with no mobile input path, so a mobile-sync timestamp has no meaning here; including it would imply a sync mechanism that doesn't exist for these entities.
- **created_by/updated_by kept as `uuid` FK to user** (not the ERD's literal `string` type) for corporate/company/business-unit — consistent with how every other entity in this catalog references the acting user (weighbridge-record.created_by, grading-record.created_by, etc. are all uuid FK), rather than introducing a one-off plain-string convention just for these three entities.
- **company.last_update (date, optional) added per ERD's `company_last_update`** — kept genuinely separate from `updated_at` (system timestamp) since it's presumed to represent something like "last reported to head office," a business-meaning date distinct from the technical audit timestamp; flagged as an inference since the ERD gives no further description of its purpose.
- **User entity's ERD divergence (nik/full_name/role_code vs current username/name/role, business_unit_code vs business_unit_id) intentionally NOT adopted this round** — out of scope for the master-data screens (027-031/033) currently being reworked; touching User would cascade into already-shipped Login/Auth screens 001-004 and screen-032 (Kelola User & Role, not yet built). Left as a separate, future concern — not silently expanded into this round's scope.
- **ERD's other 5 future-station entities (sterilizations, threshings, pressings, depricarpings, kernel_plants) and their _details/_operational_targets tables intentionally NOT added** — these are the "12 placeholder stations" the PRD explicitly defers past MVP; only the master-data entities needed for screens 027-031/033 were touched this round.
